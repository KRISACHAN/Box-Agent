# 方法论：从澳门旅行助手到城市旅行 Skill 开发

## 1. 核心判断

城市旅行助手不是“把攻略写进提示词”，而是建立一套可持续回答的城市知识系统。澳门项目的经验表明，一个旅行 Skill 是否能进入上架候选，关键不在于文案像不像攻略，而在于是否具备：

1. 可追溯的资料地图；
2. 官方事实与攻略表达分层；
3. 可组合的路线分支；
4. 对实时变化的核验机制；
5. 完整输出样例；
6. 覆盖差异场景的模拟回归；
7. 干净上传包与可解释评分。

## 2. 七段式开发法

```text
资料地图 → 蒸馏 → 建模 → 样例 → 回归 → 门禁 → 评估
```

### 2.1 资料地图

先列资料来源、来源层级和缺口，而不是直接写路线。资料地图要区分：

- 官方事实层：稳定事实和权威入口。
- 交通与空间层：抵达方式、口岸/车站/机场、区域关系。
- 景点与体验层：核心 POI、适合人群、排队与体力成本。
- 攻略表达层：用户常问方式、社媒表达、避坑经验。
- 实时核验层：会变的信息。

### 2.2 蒸馏

蒸馏不是摘要。蒸馏要把资料转成决策规则，例如：

- 什么人适合这条线；
- 什么情况下要换线；
- 哪些内容必须提醒核验；
- 哪些社媒说法只能作为表达线索。

### 2.3 建模

建模是把城市转成可调用知识资产：概览、路线、场景、异常、核验、FAQ。这样 Agent 回答时才能按任务加载，不会每次重新发散。

### 2.4 样例

至少 3 个完整样例，承担“展示能力边界”的作用。样例不能只有标题，要包含适用人群、路线、节奏、预算提醒、实时核验和降级方案。

### 2.5 回归

回归记录要覆盖真实差异：入口、时长、人群、预算、天气、实时信息。模拟回归必须写明是模拟，不能冒充线上日志。

### 2.6 门禁

源目录可以有污染，但上传包必须干净。发现 `.DS_Store`、云同步隐藏文件、嵌套 ZIP、历史占位符、本机路径泄露时，应阻断上传并重建干净目录。

### 2.7 评估

TRACE 评价结构可信度，Depth 评价专业厚度。评分是静态预审，不等同真实线上表现。

## 3. 与普通旅行规划的区别

| 项目 | 普通旅行规划 | 城市旅行 Skill 开发 |
|---|---|---|
| 目标 | 回答一次行程 | 生成可复用技能包 |
| 输入 | 用户出行需求 | 城市资料、用户场景、平台规则 |
| 输出 | 一份行程 | SKILL.md、知识库、样例、回归、门禁、ZIP |
| 风险 | 行程不合适 | 事实过期、误触发、上传污染、能力空壳 |
| 成功标准 | 用户能参考出行 | 可触发、可执行、可校验、可上架预审 |

## 4. 最小可交付标准

一个 release-ready 城市旅行 Skill 至少应包含：

- 根入口 `SKILL.md`；
- `README.md` 与 `package.json`；
- `knowledge/index.md` 和至少 4 个核心知识文件；
- `examples/` 下至少 3 个完整输出样例；
- `templates/` 下通用行程、回归、实时核验模板；
- `qa/source-map.md`、`qa/regression-records.md`、`qa/quality-gate.md`、`qa/scoring-rubric.md`；
- 干净 ZIP，无隐藏文件、嵌套 ZIP、不支持文件和隐私泄露。
