# 非文化主导城市旅行 Skill 开发手册

## 1. 使用场景

当目标城市或目的地不是以博物馆、古建、历史街区、考古遗址为主要吸引物，而是由度假、购物、美食、户外活动、亲子娱乐、节庆活动等体验驱动时，使用本手册。

典型目标包括：

| 类型 | 典型用户意图 | Skill 开发重点 |
|---|---|---|
| 海岛度假型 | 想放松、亲海、住得舒服、拍照好看 | 季节天气、海滩分区、酒店带宽、交通接驳、水上活动、安全与预算 |
| 购物消费型 | 想买得顺、退税方便、少踩坑 | 商圈分层、品牌/奥莱/本地买手店、营业时间、退税规则、交通与寄存 |
| 美食驱动型 | 想吃到代表性餐厅和街区 | 菜系地图、预约规则、排队成本、食品安全、预算分层、避坑策略 |
| 户外徒步型 | 想走路线、看自然风景、保证安全 | 路线难度、季节窗口、装备、补给点、救援/保险、天气降级 |
| 亲子休闲型 | 想省心、轻松、安全、有备选 | 动线短、设施全、儿童友好、午休/避暑、医疗与应急 |
| 节庆活动型 | 想围绕赛事、演出、节庆安排行程 | 票务、交通管制、人流峰值、住宿溢价、散场方案 |

**边界提醒**：本手册用于“开发城市旅行 Skill”，不是直接替用户实时预订酒店、购买门票、承诺库存或替代当地安全/医疗/法律建议。

## 2. 核心转向：从文化解释力转为体验交付力

文化型城市的核心问题是“为什么值得看、怎么看懂”。非文化型目的地的核心问题是“怎么选、怎么排、怎么避坑、怎么按人群和预算稳定交付体验”。

因此，开发 Skill 时要把知识结构从“文明线索”切换为“四张体验地图”：

1. **体验地图**：用户真正想获得什么体验，如躺平、买货、吃饭、徒步、亲子放电。
2. **约束地图**：天气、营业时间、预约、预算、体力、交通、人流、语言、支付、退税。
3. **风险地图**：季节关闭、台风/暴雨、高反/中暑、食品安全、假货、交通中断、排队过长。
4. **降级地图**：天气不好、孩子累了、餐厅约不到、徒步不适合、购物超预算时怎么办。

## 3. 输入检查

开发前先让用户补齐以下信息；缺失时给默认假设，但必须在输出中标注。

| 字段 | 必填性 | 用途 |
|---|---|---|
| 目的地/城市范围 | 必填 | 确定资料边界，避免把周边岛屿或商圈混入 |
| 目标人群 | 必填 | 情侣、家庭、亲子、银发、朋友、独行、摄影、轻奢等 |
| 主导体验 | 必填 | 海岛、购物、美食、徒步、亲子、节庆，可多选但需排序 |
| 出行月份/季节 | 强建议 | 决定天气、开放时间、活动窗口和安全边界 |
| 天数与节奏 | 强建议 | 决定路线密度和降级空间 |
| 预算档位 | 强建议 | 决定酒店、餐厅、交通和购物建议深度 |
| 是否需要实时信息 | 必填判断 | 门票、营业时间、天气、交通、退税等必须实时核验 |

## 4. 资料采集优先级

| 信息类型 | 优先来源 | 不足时降级 |
|---|---|---|
| 天气与季节 | 官方气象、旅游局、国家/地区气象机构 | 近年旅行平台趋势，仅作经验参考 |
| 交通与开放 | 官方交通、机场/港口、景区/商场/餐厅官网 | 地图平台与近期用户评论交叉验证 |
| 购物退税 | 海关/税务/机场/官方商场说明 | 旅行平台攻略仅作线索 |
| 餐厅预约 | 餐厅官网、官方社媒、预订平台 | 榜单平台 + 近期评论 |
| 徒步安全 | 官方公园、保护区、登山协会、救援机构 | 户外社区经验，但必须标注风险 |
| 酒店度假 | 酒店官网、官方设施说明、近期评价 | OTA 评论拆分到房型/海滩/亲子/交通维度 |

**禁止把社区攻略当成唯一事实来源。** 社区经验可以帮助发现坑，但不能替代官方开放时间、票务、天气、安全规则。

## 5. 分类型开发模板

### 5.1 海岛度假型

开发重点：
- 把海滩/岛屿/酒店区按体验分区：安静、亲子、潜水、夜生活、摄影、奢华、性价比。
- 标注季节窗口：雨季、台风、海况、能见度、水上项目开放概率。
- 设计“住哪里决定怎么玩”的路线逻辑，而不是把景点平铺。
- 给出天气降级：暴雨日、风浪大、晒伤/中暑、航班/船班延误。

输出模块建议：
- `island-area-selector.md`：住宿区域选择器。
- `weather-and-sea-condition-gate.md`：天气与海况门禁。
- `relaxation-route-templates.md`：躺平、亲子、水上活动、摄影路线模板。
- `safety-and-backup-plan.md`：台风、船班、急救、保险提示。

### 5.2 购物消费型

开发重点：
- 把商圈分成奢侈品、奥莱、本地设计、药妆/日用品、电子产品、买手店。
- 用“购买目标 + 时间成本 + 退税/寄存 + 交通”组织路线。
- 明确营业时间、退税规则、支付方式、假货/水货风险。
- 设计陪同者体验：不购物的人在哪里休息、吃饭、带娃。

输出模块建议：
- `shopping-district-map.md`：商圈和品牌类型地图。
- `tax-refund-and-logistics.md`：退税、寄存、行李和机场衔接。
- `one-day-shopping-route.md`：半日/一日/两日购物路线。
- `anti-pitfall-checklist.md`：价格、真伪、售后、退换货风险。

### 5.3 美食驱动型

开发重点：
- 从“餐厅清单”升级为“菜系地图 + 用餐场景 + 预约规则”。
- 区分排队型、预约型、街区扫吃型、市场型、精致餐饮型。
- 给出饮食限制：儿童、老人、过敏、素食、清真、食品安全。
- 处理时间约束：早餐/午餐/晚餐/夜宵与景点动线结合。

输出模块建议：
- `food-neighborhood-map.md`：美食街区与菜系地图。
- `reservation-and-queue-rules.md`：预约、排队和替代餐厅规则。
- `meal-route-templates.md`：早餐、午餐、晚餐、夜宵路线。
- `dietary-risk-checklist.md`：过敏、卫生、酒精、儿童友好。

### 5.4 户外徒步型

开发重点：
- 路线必须按难度、海拔、距离、累计爬升、路况、季节窗口分级。
- 明确“不建议去”的条件：极端天气、装备不足、儿童/老人不适合、单人风险。
- 设计补给、交通、撤退点、通信、保险、救援信息。
- 输出必须有安全声明：Skill 不替代当地官方安全指引。

输出模块建议：
- `trail-difficulty-matrix.md`：路线难度矩阵。
- `season-and-weather-gate.md`：季节和天气门禁。
- `gear-and-safety-checklist.md`：装备与安全清单。
- `bailout-and-rescue-plan.md`：撤退点、补给、紧急联系。

## 6. 输出契约

非文化主导城市 Skill 至少应包含：

1. **用户分层入口**：按人群、预算、季节、主导体验选择路线。
2. **体验选择器**：帮助用户在相似区域/路线/商圈/餐厅之间做选择。
3. **实时核验清单**：哪些信息必须出行前核对。
4. **降级方案**：天气、排队、预约失败、体力不足、预算变化时怎么改。
5. **安全与边界声明**：尤其是海岛、户外、食品、购物退税。
6. **示例 Prompt**：让普通用户知道如何调用这个城市 Skill。

## 7. 质量门禁

- [ ] 是否明确标注该城市/目的地的主导体验？
- [ ] 是否按人群、季节、预算、天数分层？
- [ ] 是否把实时信息与稳定知识分开？
- [ ] 是否给出至少 3 个降级场景？
- [ ] 是否说明哪些建议需要出行前再次核验？
- [ ] 是否避免把非文化城市硬套历史文化框架？
- [ ] 是否避免变成泛泛景点清单或餐厅榜单？

## 8. 常见反模式

| 反模式 | 问题 | 修正方式 |
|---|---|---|
| 把海岛写成景点大全 | 用户真正关心住哪、天气、海况和体验节奏 | 改成区域选择器 + 天气海况门禁 |
| 把购物城市写成商场名单 | 缺少购买目标、退税、交通、寄存 | 改成购物任务流和风险清单 |
| 把美食城市写成餐厅榜 | 忽略预约、排队、饮食限制和动线 | 改成菜系地图 + 预约/替代规则 |
| 把徒步城市写成美景推荐 | 有安全风险，缺少难度和撤退 | 改成路线难度矩阵 + 安全门禁 |
| 为了显得深度强行加历史 | 偏离用户动机 | 文化内容作为背景，不抢主线 |
